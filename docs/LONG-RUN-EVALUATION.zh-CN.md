# 长任务对照实验方案

状态：方案已准备，真实模型长任务尚未执行。现有本地脚本 API 测试
只证明工程边界，不提供模型能力、真实 token 或 KV 缓存收益结论。

## 要回答的问题

第一阶段比较 `restart` 与 `reuse`：两者都遵守 LoopForge 的干净
调用契约，主要检验宿主复用是否降低开销、是否引入状态残留或不稳定。
不能把它们的差异解释成“清空上下文与保留对话”的差异。

第二阶段才评估任务连续性：观察经过多轮清空后，Agent 是否重复调查、
遗漏已提交发现，或无法利用已提供的 Working Memory。先找具体案例，
再决定是否调整同一份提交记录的确定性投影；不新增适配器记忆库。

## 固定任务与实验夹具

准备一个独立的 TypeScript 示例项目，不在 LoopForge 或适配器源码
目录中执行任务。固定目标如下，作为新 loop 的 operator 输入：

> 实现一个本地依赖任务运行器。输入为 JSON 任务图；校验重复 ID、
> 缺失依赖和环；按确定顺序调度可运行任务，遵守并发限制；支持失败
> 重试、失败依赖的跳过、运行取消和超时；输出结构化事件与最终结果。
> 提供程序 API 与读取 JSON/输出 JSONL 的 CLI，并说明失败退出码。
> 使用 TypeScript、Node.js >=18、零运行时依赖。任务拆分、轮次边界、
> 工具选择和是否完成由 Agent 决定，按 LoopForge 实时指导提交。

正式执行前，需要将以下夹具内容实现并冻结为一个 Git 提交：

- 最小项目骨架、明确的 API/输入输出规范、示例和运行命令。
- 覆盖图校验、确定顺序、并发、重试、跳过、取消、超时、CLI 的
  固定验收测试；取消和超时使用受控时钟或同步点，避免依赖短暂等待。
- 一个说明测试运行方式的静态技能及一个无会话记忆的本地工具服务，
  用于观察技能可用性和 MCP 启动行为。内容与版本在各组完全相同。
- 按当前 LoopForge 支持的配置绑定独立 after-phase 验证命令，固定
  测试入口及配置。Agent 的成功报告不代替命令观察。

这些夹具目前不是本仓库已经提供的可执行基准。冻结后记录其提交
哈希、任务文本哈希及验证命令；首轮试跑只检查夹具可运行性。
如果试跑暴露规范问题，修订后重新冻结，不在正式比较中途改题。

## 对照条件

| 项目 | A 组 | B 组 |
| --- | --- | --- |
| 宿主模式 | `restart` | `reuse` |
| 模型 | `deepseek-flash[1m]` | 相同模型与 provider 配置 |
| 初始代码、验收与静态技能 | 冻结的夹具提交 | 同一提交的独立副本 |
| LoopForge、适配器、Claude、Node | 固定版本/提交 | 完全相同 |
| 上下文契约 | 按 LoopForge 返回值执行 | 完全相同 |
| 初始历史 | 新工作区、新 loop，无旧 Vault | 独立新工作区、新 loop，无旧 Vault |

先跑一对检查可行性，再按 A1、B1、B2、A2、A3、B3 的预定顺序
取得三对样本。每次都从冻结夹具开始，不能把前一组完成的代码或
工具服务内存带进后一组。每个 run 中服务按本组宿主模式正常存活。

每次可设置 `--max-rounds 30` 作为上限，同时固定相同的外部时间
和模型费用预算。上限不是要求完成 30 轮：不得人为切小工作或强迫
Agent 继续。若实际轮次太少，记录为“长轮次证据不足”；后续另立
更大的固定任务，不能在现有 loop 中改写 operator acceptance。

## 记录什么

| 观察 | 来源与解释 |
| --- | --- |
| 提交轮次、尝试、恢复和最终状态 | LoopForge 的 committed history 与只读视图；不另计一个进度 |
| 验收命令结果 | LoopForge 命令观察及一次独立的最终复核；Agent 声明单独标注 |
| 总耗时、宿主启动/切换/交付等待 | 宿主侧单调时钟和生命周期诊断；不把时间作为轮次边界 |
| 宿主与 MCP 启动、切换失败、回退 | 测试夹具进程事件及适配器诊断 |
| token、费用和缓存命中 | provider/宿主确实暴露的记录；没有则标 unknown，不按进程复用推断 |
| 反复读同一文件或调用同一技能 | 人工复核宿主现有记录；相同路径与内容哈希只是候选，不能自动判为无效重复 |
| 丢失的重要发现 | 对照原提交、当轮实际 prompt artifact 和后续行为的具体案例 |

不为取数给运行时新增 transcript 存储、自动摘要、工具输出语义分析
或强制 provider 网关。无法取得的数据明确缺失；必要的测量扩展需
单独实现为可关闭的宿主诊断，不参与 LoopForge 的提交和成功判断。
实验报告是离线评估产物，不能回流为额外进度、契约或记忆来源。

## 如何分析连续性问题

对每个“又调查了一次”的案例，按原始记录区分：

1. 发现未被 Agent 提交，下一调用本来就没有获得保证。
2. 发现已提交，但离开窗口、被截短或整个 Working Memory 未渲染。
3. 相关内容已在当轮提示中，Agent 仍重复调查或误解。
4. 文件/服务发生了变化，重新读取实际有必要。

语义判断由人工或明确标为 Agent 分析的复核承担。适配器不能据此
自动挑选记忆；LoopForge 也不能把分析报告提升为机器证据。
尤其不能把正常的状态复查全部统计成“遗忘”。

## 失败与结论边界

输入不一致、切换未确认或退出未确认都记录为失败，不手工补回车、
篡改 prompt 或绕过 admission 把 run 修成成功。按正常恢复机制
继续时，保留原失败与恢复成本，不删除样本。暂停、超时和 provider
不可用分别记录，不将失败观察过滤掉。

报告逐对给出原始结果，再给出中位耗时与范围；失败率单独展示，
不能只平均成功样本。样本少时不作统计显著性结论。三对样本仍不足
以宣称所有项目、平台或模型都获益。

如果日后加入普通 Claude 连续对话作为参考组，要明确其缺少
LoopForge 治理这一混杂因素。不得为了制造“连续对话基线”而让
适配器忽略 LoopForge 的 `fresh_invocation`。

优先根据证据选择后续工作：交付故障改传输，服务状态残留改明确的
服务生命周期策略，环境漂移改版本/内容一致性校验；只有已提交信息
在投影中丢失的具体案例，才用于讨论 LoopForge 的投影调整。
