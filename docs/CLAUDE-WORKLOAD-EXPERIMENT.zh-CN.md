# Claude Code 真实编码与干净会话缓存实验

2026-11-13，Windows、Node.js 24.16.0、Claude Code 2.1.323、真实 DeepSeek
`deepseek-flash[1m]`。只操作独立适配器和系统临时目录；没有运行、构建或
连接主 LoopForge 项目。轮次调度由独立测试夹具提供，不是 LoopForge
端到端验收，也没有把实验记录写入 LoopForge 历史。

## 本次增加的真实性

前次实验主要让模型直接提交，验证服务端缓存身份问题。本次让真实模型
完成三步 TypeScript 开发，实际使用 Claude 的 Read/Write/Edit/Skill，
并连接一个真实 stdio MCP 服务获取数据、执行独立检查：

1. 实现 `normalizeTag`：NFC、trim、小写、合并内部空白。
2. 保留前一导出，增加 `uniqueTags`：去空、去重、保序、不修改输入。
3. 保留前一行为，增加 `countTags`：计数并使用 null-prototype 字典，
   使 `__proto__` 和 `constructor` 都可作为普通键。

能力背景是约 2 KiB 的实际编码指导，不是大量重复填充文本。第一轮还
要求真实调用一个临时原生技能；其正文带有唯一诊断标记。每轮的 fixture
工具也返回不同标记。独立检查脚本在 editable source 之外，提交时校验
其内容哈希未改变；检查命令由 MCP 服务使用 Node 执行，不以模型的成功
声明代替通过结果。临时工作区在结束后删除。

## 结果

原始标识组与后续诊断版稳定标识组均完成三轮编码，三轮独立检查均通过。
两组各一个 Claude 宿主进程、一个普通 MCP 服务进程、三个不同的原生
会话。轮次之间**没有为缓存人为添加等待**。

| 配置 | 首轮首次请求：未命中 / 命中 | 第二轮首次请求：未命中 / 命中 | 第三轮首次请求：未命中 / 命中 |
| --- | ---: | ---: | ---: |
| 原始 Claude 服务侧用户标识 | 5,039 / 0 | 5,184 / 0 | 5,189 / 0 |
| 稳定本次运行的服务侧用户标识 | 5,037 / 0 | 2,110 / 3,072 | 1,987 / 3,200 |

稳定标识组第二、三轮首次请求分别命中约 **59.3% 和 61.7%** 的输入。
这不同于前次长合成背景实验约 93% 的结果，不能把合成样本命中率直接
推广到真实编码任务。两组轮内的后续请求均出现缓存命中，原始标识组的
问题主要表现在每次干净会话开始时缓存重新变冷。

原始标识成功组共 14 次请求，约 38.8 秒；稳定标识诊断成功组共 16 次请求，
约 29.3 秒。两次模型采取了不同的工具序列、生成不同代码，而且测试夹具
后来补充了错误处理，因此这些耗时**不能作为受控提速百分比**。输入和
输出 token、请求数也不同，不能用首次请求命中率直接宣称总费用降低。

## 干净边界与技能

在请求到达真实服务之前，逐个检查了本次实验的唯一标记：

- 新轮请求没有上一轮提示标记和上一轮工具 fixture 的唯一标记。
- 第一轮原生技能正文确实展开并进入轮内请求；第二、三轮首次请求没有
  该正文的唯一标记。没有从 transcript 回放这个技能正文。
- 当前轮 fixture 结果会进入当前轮后续请求；不会被误清空。
- 原生 session ID 每轮改变；服务侧缓存域可以保持同一运行不变。
- 工作区源代码跨轮存在，模型需要时重新 Read。清空的是任务对话，并非
  撤销工作区成果。

这进一步证明了缓存复用与对话隔离可以共存，但**仍未实现把任意调用过
的技能正文或工具输出拆出来保留其计算状态**。那部分本次恰恰验证了会
随着对话清理；静态能力原文和旧对话中的动态技能展开不能混为一谈。

## 必须保留的失败样本

后续已经复现并修复实验服务的参数崩溃路径，以及正式适配器未监听原生
回答结束、CLI 返回码丢失的问题。见[可靠性定位与修复](./CLAUDE-RELIABILITY.zh-CN.md)。
以下仍是原始失败样本的证据边界，后续注入实验没有补造历史记录。

首次稳定标识真实运行未完成：第一轮 28 次模型请求，约 181 秒后超时，
外部服务只记录了 fixture，没有记录成功的 check。服务端轮内缓存一直
有命中，但有缓存并不能让任务自动完成。这个样本没有从结果中删除。

最初夹具缺少逐次工具错误记录，无法从留存数据确定该次卡住的唯一根因。
因此没有把“再次通过”写成“已修复这次失败”。后续诊断版补充了工具
错误记录、每轮最多 12 次请求、MCP 参数错误的非致命回复及服务错误记录。
这些属于实验可诊断性和请求预算约束，不是模型能力修复。

诊断版稳定标识运行通过，记录到一次 Read 文件不存在，模型随后完成了
源代码写入与三轮检查；服务端没有记录 `service-error`。这说明某些工具
错误可以在轮内恢复，不足以倒推首次超时的具体原因。不能依据一个成功
样本宣布运行可靠性已达生产标准，也不能把失败消耗排除后宣称普遍收益。

## 证据和复现

从适配器源码目录运行。默认使用本地脚本响应，验证工具执行、检查、
会话切换和观测管道；它不测量真实模型能力或缓存费用。

```powershell
npm run probe:claude-workload
```

真实 API 运行使用现有环境密钥，仅支持官方 DeepSeek Anthropic 地址。
每组最多 36 个模型请求，每轮最多 12 个，每请求输出上限 1,024 token，
每组时间上限 180 秒。`--stable-only` 只执行稳定标识组。

```powershell
npm run probe:claude-workload -- --live --output-dir experiments/results/my-workload-run
npm run probe:claude-workload -- --live --stable-only --output-dir experiments/results/my-stable-run
```

源码：[workload probe](../experiments/claude-workload-probe.ts)、
[实验转发与 SSE 用量观测](../experiments/anthropic-probe.ts)。

只读最终累计用量，以及转发前拒绝过大的输出上限。
